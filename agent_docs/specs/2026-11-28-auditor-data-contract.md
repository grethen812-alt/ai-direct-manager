## 1. Область и общий формат

Первый сценарий охватывает один продукт, одну разрешённую пару кабинет–счётчик,
одну кампанию с двумя объявленческими связками и один закрытый период. Сопоставляем
расходы, измеренные цели и качество лидов CRM. Оцениваем квалификацию на дату
среза и отдельно показываем возможные более свежие сигналы из Метрики.
Бизнес-эффект и качество артефакта оцениваются отдельно.

- **Обязательные поля** нужны для соответствующей проверки. Пропуск блокирует вывод
  в затронутом разрезе, а отчёт перечисляет, что осталось доступно.
- **Дополнительные поля** уточняют вывод или открывают детализацию. Отсутствие
  отражается как «нет данных», «не применимо» или «не утверждено».
- Сырые ID рекламных объектов, счётчиков и целей хранить как строки без округления,
  денежные значения — в десятичном формате с валютой и признаком НДС. Персональные
  данные в контракт не входят. Сопоставление событий выполняется в закрытой среде,
  наружу передаются агрегаты и обезличенные ссылки на доказательства.
- Для всех источников обязателен манифест с версией схемы, видом источника,
  ссылкой или хешем среза, разрешённой областью, часовым поясом, периодом,
  временем выгрузки, запросом или версией фильтра, количеством строк,
  статусом покрытия и причинами пропусков. Для Метрики сохраняются семплирование,
  модель атрибуции и тип показателя. Неизвестные параметры явно обозначаются.

## 2. Директ

| Набор и гранулярность | Обязательные поля | Дополнительные поля |
| --- | --- | --- |
| Реестр кампаний, групп и объявлений | Область кабинета из доверенной настройки, ID кампании, группы и объявления, родительские ID, тип и статусы, время получения | Названия, дата старта, бюджет, минус-фразы, регионы, тип устройства |
| Расходы, день × кабинет × кампания | `Date`, `CampaignId`, `Cost`, валюта, НДС и денежная единица. `Impressions` и `Clicks` обязательны для диагностической части контрольного сценария. | Сеть, география, устройство, атрибуция целей, поисковые запросы, тип критерия |
| Расходы, день × объявление | `CampaignId`, `AdId`, дата, показы, клики, расход, параметры из кампанийного отчёта. Нужны для сравнения двух связок. | `AdGroupId`, площадка, сегмент, версия объявления, если достоверна на дату показа |
| Снимок рекламной связки | ID объявления, активная версия креатива и посадочной с интервалами действия или явный признак недоступной версии. Нужен для выводов на уровне конкретной версии. | Тексты, заголовки и URL из объявления, семантика, версия формы, визуальное описание и ссылка на объект в закрытом хранилище |

**Уже доступно в MCP.** `yd_campaigns_get` возвращает базовую структуру кампаний,
`yd_adgroups_get` — группы, родительские ID, регионы и минус-фразы,
`yd_ads_get` — объявления и доступные тексты и ссылки обычных и комбинаторных
форматов, `yd_keywords_get` — фразы, ставки и настройки автотаргетинга.
`yd_report` принимает даты, тип отчёта, колонки и фильтр по ID кампаний.
Для пилота проверить комбинации `Date`, `CampaignId`, `AdId`, `Cost`,
`Impressions`, `Clicks` с кампанийным и объявленческим типами отчётов.
Пустой `AdId` относится к отдельной строке «без объявления» и остаётся в сверке.
Денежный TSV профиля возвращается без микроединиц, с НДС и без скидки,
как задано в коде. Валюту подтверждает владелец по авторитетному источнику.

**Нужно дополнительное получение данных.** История версий объявлений и посадочных,

API форме, которую можно выразить имеющимися полями инструмента. Проверка
совместимости разрезов остаётся условием приёмки.

артефакт для F‑01 можно получить из утверждённой обезличенной выгрузки формы
или трекинга. Источник и разрешённые поля утверждает владелец. Без него F‑01
остаётся агрегированной сверкой с явно ограниченным вердиктом.

## 4. CRM через Google Sheets

Источник — вручную обновляемая пользователем выгрузка Битрикс24 в Google Sheets.
Интеграция напрямую с Битрикс24 не планируется. Дата последней редакции листа
не заменяет подтверждённое время выгрузки из CRM.

| Колонка выгрузки | Использование в аналитическом наборе |
| --- | --- |
| ID лида CRM | Обязательный устойчивый ключ. Псевдонимизируется в частной зоне. |
| Название лида | Есть в исходной таблице. Свободный текст исключается из входа модели. |
| Источник | Сохраняется в очищенном виде. Значение и версия справочника нужны для проверки атрибуции. |
| Проект | Используется для области и фактического продукта по утверждённой карте. Неопределённый проект учитывается отдельно. |
| Дополнительные сведения об источнике | Дополнительные данные для проверки. Передаются только разрешённые структурированные признаки. |
| Стадия CRM | Снимок исходного значения. Нужна для квалификации, распределения по категориям и исключения тестов. Пустое или неизвестное значение не превращается в присвоенную категорию. |
| Дата создания | Обязательна для когорты и отбора визитов. Указывается часовой пояс. |
| Roistat | Дополнительное поле. Формат и доказательность значения подтверждает владелец. |
| Metrika Client ID | Доступен в части выгрузок. Сохраняется как текст без потери точности, в закрытом контуре. Отсутствие фиксируется отдельно. |

Обязательные метаданные среза — время и часовой пояс ручной выгрузки из CRM,
версия или хеш выгрузки, лист или диапазон, область и версия справочника.
Дата смены стадии и версия отдельной строки отсутствуют в подтверждённом наборе.
Их можно использовать, если появится авторитетный источник. В пределах одного
среза точные повторы строк по ID схлопываются. При конфликте стадий одного ID
без подтверждённого порядка ID учитывается один раз, а затронутые показатели
классификации и исключения тестов помечаются как неполные. Если записи
противоречат друг другу по признаку теста, точный валовой итог по затронутому
разрезу не утверждается до сверки.

Google Sheets остаётся неизменным. Более свежие сигналы хранятся отдельно
с ID лида, исходной стадией и датой CRM-среза, доказательствами офлайн-событий,
временем события, загрузки и обнаружения, предполагаемым или подтверждённым
этапом, источником и достоверностью сопоставления. Сигналы не меняют
срез CRM и его официальные KPI. [Схема обогащения](2026-11-28-auditor-offline-attribution.md#два-независимых-результата-сопоставления)

**Доступность.** Восемь MCP-инструментов не читают Sheets. Для будущего пилота
нужен ограниченный коннектор чтения или утверждённый артефакт выгрузки.
CRM, браузерные ключи и свободный текст остаются в частном контуре.

## 5. Вордстат

| Набор и гранулярность | Обязательные поля | Дополнительные поля |
| --- | --- | --- |
| Запрос × период × регион × срез устройства | Исходная фраза с операторами, ID кластера из утверждённой семантики, регион, интервал, гранулярность, срез устройства, число запросов, время выгрузки | Связанные запросы, региональное распределение, нормализованная доля, версия утверждённой кластеризации |

Сравнивать одинаковые фразы, операторы, регионы, устройства и равные по длине
периоды. Пересекающиеся запросы не суммируются в уникальный спрос. Результат —
контекст спроса и проверяемая гипотеза, а не источник атрибуции заявок.
В синтетическом контроле этот блок обязателен, при недоступном реальном источнике
его отсутствие не блокирует базовую сверку рекламы и CRM.

**Доступность.** В восьми инструментах Вордстата нет. В основном сервере есть
обработчики динамики, регионов, популярных запросов и дерева регионов.
Для пилота потребуется отдельно ограниченное чтение или утверждённая выгрузка.
[Инструменты Вордстата в основном сервере](../../server.py#L1071-L1125)

## 6. Правила сопоставления

1. Сначала применить утверждённый реестр «кабинет — счётчик — продукт —
   кампания — период действия». Приоритетный продукт кампании и фактический
   продукт заявки хранить отдельно. Сравнивать одинаковые срезы валюты,
   НДС, часового пояса, атрибуции и временной базы. Дата клика, дата достижения
   цели и дата регистрации в CRM имеют самостоятельный смысл.
2. Структуру Директа соединять по области и стабильным ID. Метрику с Директом
   можно соединять на агрегированном уровне по подтверждённой связи кабинета,
   ID кампании или объявления и согласованному срезу. Сверить кампанийный отчёт
   с суммой непересекающихся строк объявлений и строкой без объявления.
3. Для F‑01 сопоставлять CRM и отдельные события по утверждённому ключу отправки
   или разрешённому связующему справочнику. Дедуплицировать технические повторы
   события отдельно от лидов. Различать `matched`, `ambiguous`, `unmatched`
   и `no_evidence`. Хранить основание связи и наиболее глубокий доказанный
   уровень — источник, кампания, объявление, версия креатива, версия посадочной.
   Совпадение UTM, названия или URL само по себе остаётся гипотезой.
4. Если CRM не даёт атрибуцию, браузерный Metrika Client ID используется для поиска
   кандидатов-визитов в пределах счётчика и согласованного окна. Конверсия и рекламный
   визит проверяются отдельно. Сопоставление по браузерному ID и времени само по себе
   не определяет конкретный лид. [Офлайн-сопоставление](2026-11-28-auditor-offline-attribution.md)
5. Страницу входа и страницу отправки хранить раздельно. Разносить заявки
   по версиям материалов только при наличии подтверждённой связи с версией в момент
   события. Кампанийный остаток не распределяется между объявлениями, а неизвестный
   источник не приписывается к Директу. НДС, валюту и единицы сверять до расчётов.
6. Проверять полноту, ограничения 90 секунд, 31 день, 1 000 строк и 128 КиБ,
   пропуски и семплирование. Для объёмных наборов дробить выборки без пересечения
   и сверять итоги. Уникальных пользователей не суммировать между срезами,
   доли пересчитывать из общих числителя и знаменателя.
   [Текущие ограничения профиля](../guides/phase1-readonly.md#ограничения-отчётов)

## 7. Утверждённая методология и справочник метрик

Цель — повышение качества лидогенерации. Приоритеты оценки по порядку:

1. Увеличение числа квалифицированных лидов.
2. Увеличение их доли.
3. Сокращение числа и доли мусорных лидов.
4. Оптимизация стоимости квалифицированного лида.
5. Контроль объёма и стоимости валовых лидов.

Снижение валового объёма и рост CPL допустимы при улучшении бизнес-результата.
CTR и CPC используются в диагностике. Вывод для кампании, объявления,
креатива или посадочной требует доказанную связь лидов с этим разрезом.

| Запись справочника | Утверждённое правило или назначение |
| --- | --- |
| `gross_leads` | Все разные ID в выбранном CRM-срезе, кроме тестовых. В том числе мусорные, бизнес-дубли, действующие клиенты, неизвестные и архивные статусы. |
| `qualified_leads` | Только два утверждённых значения исходной стадии из закрытого справочника. Не определяется по названию категории, сегменту, сходству строк или более свежему сигналу Метрики. |
| `trash_leads` | Лиды категории «Мусорные» по действующей утверждённой версии справочника. |
| `qualified_share`, `trash_share` | Соответствующее число лидов / валовые лиды в той же области и когорте. |
| `qualified_cpl`, `gross_cpl` | Сопоставимый расход / квалифицированные или валовые лиды в том же разрезе. |
| `crm_distribution` | Все восемь утверждённых категорий, включая тесты, плюс две отдельные группы — неизвестные и архивные статусы. Не относить эти две группы к действующим категориям. |
| Воронка и диагностика | Достижения и целевые визиты Метрики отдельно, CTR = клики / показы, CPC = расход / клики. Встречи и продажи — по утверждённому источнику и правилам. |

Отдельная метрика «Рабочие лиды» исключена. Строки листа не увеличивают число
лидов при повторном появлении ID. Лид, попавший в категорию «Дубли», учитывается
в валовых как самостоятельный CRM-ID. Тест исключается до расчёта валовых KPI,
но сохраняется в распределении. Неизвестный и архивный статус показываются
отдельно и не классифицируются моделью. Нулевой или неизвестный знаменатель
даёт «не рассчитано». Расчёт качества сопровождается временем выгрузки и
признаком зрелости.

Запись справочника содержит ключ, единицу, гранулярность, формулу или правило
подсчёта, исключения, источник, временную базу, атрибуцию, зрелость, покрытие,
версию, статус утверждения и владельца. Два точных значения исходной стадии,
полная карта восьми категорий, синонимы и архивные записи хранятся в утверждённом
закрытом справочнике. Публичный контракт задаёт способ проверки этого списка.
Различать `computed`, `not_approved`, `missing_data` и `not_applicable`.
Число 0 означает проверенное отсутствие.

## 8. Решения владельца данных

1. Кто утверждает пилотную область, источник времени среза, историю обновлений
   и карту «проект — кабинет — счётчик — кампания»?
2. Где будет храниться закрытый утверждённый список двух стадий, карта восьми
   категорий, признаки тестов и отдельный перечень архивных стадий?
